## New findings from subagent tracks (enforcement / data-layer / release / UI)

### Enforcement & time-accounting (subagent track A) — all resolved
- [x] [HIGH] Day-rollover reset silently bypassed on hydration — `hydrateFromRoom()` stamped `currentEpochDay = today` unconditionally while loading each restriction's `consumedSeconds`/`consumedEpochDay` raw from Room with no day check, neutering `resetDayIfNeeded()`'s mismatch detection for the rest of that day. Failure scenario: reboot/service-restart at a moment Room holds yesterday's near-exhausted consumedSeconds → false "quota exhausted" block starts immediately with zero real usage that day, persisting until the next calendar day. FIXED: ParentalControlState.kt hydrateFromRoom now resets any restriction whose stored day != today (mirroring resetDayIfNeeded's own per-snapshot logic), gated by the same clock-tamper check (below) so a service restart can't launder a tampered clock into an early reset.
- [x] [HIGH] No dynamic launcher/home-package exclusion — EXCLUDED_PACKAGES was a static list with no launcher entry; device/OEM launcher package varies and isn't safe to hardcode. If a parent ever restricted a package that happens to be (or share identity with) the active launcher, the home screen itself would become unreachable with no way back to Settings/ScrollGuard (device-brick risk), directly violating spec Issue I. FIXED: BlockerAccessibilityService.onServiceConnected() now resolves the current CATEGORY_HOME package via PackageManager.resolveActivity() and registers it with ParentalControlState.registerLauncherPackage(); isAppQuotaExhausted/isParentallyRestricted/isExcludedFromBlocking all route through a shared isSelfOrSystemPackage() check that includes it.
- [x] [CONFIRMED GAP, spec Issue F] Clock-tamper detection was entirely unimplemented — day-rollover keyed purely on device wall-clock LocalDate.now() with no defense, so a child could open Settings (not blocked) and wind the clock backward to trivially reset consumedSeconds to 0 and grant unearned time. FIXED: added ParentalControlState.isClockTamperedBackward(context) — compares a persisted boot-time estimate (wall-clock minus elapsedRealtime, stable across one boot session) against the current one to distinguish a genuine reboot (elapsedRealtime legitimately resets) from a clock wound back with no matching reboot. Persisted in a dedicated SharedPreferences file (not Room — avoids a schema migration; kept separate from TimerState's own prefs per invariant #5). Wired into both resetDayIfNeeded() and hydrateFromRoom(). Local-only heuristic — does NOT do the spec's further-mentioned online serverTimestamp reconciliation; noted as a known limitation, not a full implementation of Issue F's "when online" refinement.
- [x] [LOW] incrementConsumed narrow race — already fixed earlier in this session (lookup moved inside the synchronized block).
- [x] [LOW-MEDIUM, resolved as documented-not-fixed = AUDIT_REPORT.md M4] Tick loop increments a flat +1 per Handler callback rather than measuring an actual elapsedRealtime() delta since the last tick (BlockerAccessibilityService.kt tickParentalTime/parentalTickRunnable). Deviates from the spec's literal mechanism but does NOT reintroduce double-counting or reboot-corruption (no elapsed baseline is persisted/compared across reboot) — net effect is a systematic small UNDERcount under scheduling jitter/GC pauses, i.e. fails in the safe direction. Deferred: real-world drift magnitude needs on-device measurement (Robolectric can't exercise real Handler/main-looper timing fidelity), and the fix is invasive relative to its benefit given it fails safe already. Recommend for a future pass.

## Decisions / deferred-by-design (not bugs, scope calls made during the audit)
- Orphaned Firestore subcollection docs after unpair (config/current, status/current, catalog/current, apps/*, requests/*) are NOT recursively deleted by PairingManager.unpair() (which only deletes the top-level family doc — Firestore never cascade-deletes subcollections). Decided NOT to add delete rules + client-side recursive cleanup for this: it's a low-severity storage/hygiene cost (orphaned docs are unreachable and inert, not a security hole), and doing it properly needs either a Cloud Function or non-trivial client-side collection listing+batch-delete, which is disproportionate complexity for a low-severity item. Documented as a known limitation in the final report instead.
- FCM Cloud Function trigger (server-side, would need deployment to the live Firebase project `scrollguard-aba84` and Blaze billing plan) is being treated as a decision requiring explicit user go-ahead, not something to deploy unilaterally — consistent with treating deploys to shared/live infrastructure as needing confirmation. Client-side receiving plumbing (FirebaseMessagingService, token storage) is being implemented regardless since it's zero-risk/inert until a trigger exists.

## Notes / Assumptions Log
- Clock-tamper detection (spec Issue F) implemented as a local-only heuristic (boot-time-estimate vs. wall-clock), not the spec's further-mentioned "when online, anchor via Firestore serverTimestamp" refinement — smallest reasonable, most-secure choice given implementing full server-reconciliation would need a schema migration and more surface area for a spec detail described as an enhancement, not the core requirement.

Implemented the one fallback path that WAS fixable without a deploy decision (sync-on-app-open) as a partial, real mitigation.
- Orphaned Firestore subcollections after unpair: decided not to add recursive client-side cleanup or extra delete rules — see "Decisions / deferred-by-design" above for the full reasoning (disproportionate complexity for a storage-cost-only issue).
